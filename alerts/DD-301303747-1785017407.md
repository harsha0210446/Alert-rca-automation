## Root Cause Analysis
**What fired**
p95 request latency for rio-offer-engine exceeded 0.6s over a 10-minute window.

**When**
Triggered 2026-07-26 03:40 IST, recovered 2026-07-26 04:26 IST.

**Root cause (likely)**
rio-offer-engine's p95 latency repeatedly breaches threshold because its Feign client calls to the beat-plan-service dependency (BeatPlanService.fetchBeatRetailers, called during offer validation/enrichment) intermittently receive 503s / connection resets. Under Feign's retry and connection-handling behavior, these failures inflate request latency for the calling endpoints (e.g. POST /api/offerEngine/event/order) enough to push p95 over 0.6s. This is a long-standing, recurring dependency-stability issue with beat-plan-service, not caused by anything in rio-offer-engine itself or a recent deploy.

**Confidence**: High — 340 error spans in 24h all point to the identical failure signature (beat-plan-service 503/connection-reset), directly on the request path of the alerting endpoint, with no competing deploy or infra-change event to explain it instead.


## Suggested Fix
- This is the real fix target: investigate beat-plan-service's stability/capacity directly — repeated 503s and connection resets under load suggest it's undersized, hitting connection limits, or has its own intermittent issue.
- In rio-offer-engine, consider a fallback/circuit breaker around BeatPlanService.fetchBeatRetailers (BeatPlanService.kt:31) so beat-plan-service instability degrades gracefully instead of inflating p95 latency on the order-event path.
- Consider whether beat-plan-service data is cacheable for short windows to reduce call volume/blast radius.
